# Architecture — estado atual

Uma foto de como o bot está montado hoje. Atualize sempre que uma feature mudar
a forma do sistema.

## Build

`src/main.js` é a entrada. O `grunt` (`grunt-scripts/mergeFiles.js`,
`module-concat`) empacota o grafo de `require` em `dist/main.js`, que é o que o
Screeps roda. `dist/main.js` é git-ignored e reconstruído a cada mudança.

## Tick flow (`src/main.js`)

```
profiler.wrap →
  memory.wrap →                         (pula o Memory JSON.parse em ticks consecutivos)
    Game.myRooms = salas próprias
    guard → planStore.activate()          (ativa os RawMemory.segments dos planos p/ o próximo tick)
    para cada sala visível:   guard → roomLogic.getIntel(room)
    para cada sala própria:   guard → roomLogic.planCity(room)
    para sala c/ Memory.layoutRequests[x] e visível, não própria:
                              guard → roomLogic.planCity(room, {preview:true})
    para cada sala própria:   guard → roomLogic.spawning(room)
    para cada creep:          guard → roleLogic[role].run(creep)
    GC de Memory.creeps dos mortos
    para cada estrutura própria: guard → structureLogic[type].run(structure)
    GC de Memory.structures das mortas
    guard → pixel (Game.cpu.bucket cheio → Game.cpu.generatePixel(), ROADMAP 0045)
    guard → utils.stats()
```

`guard(label, fn)` faz try/catch para que uma falha nunca aborte o tick. O
profiler só carrega quando `Memory.settings.profiler` está setado.

| `reservations.js` | Resolve disputa por pilha de energia. Ledger por tick (`creep.memory.loadTarget`). `available(creep, pile)` = energia livre p/ o creep depois de descontar quem tem prioridade — 3 ranks (`pickerRank`, maior ganha): **pioneer (2)** > hauler/bootstrap (1) > todo mundo (0). Cedendo a pilha **inteira** num drop/tombstone/ruína (descartável, único) vs. só o quanto o ranking mais alto ainda precisa num container/storage/link (`isReplenishing`, tem `structureType`) — mesma regra pra qualquer par de ranks. Lido por `rooms/needs.js` (contagem de scout), `roles/scout.js` (pula sala já coberta por observer) e `structures/observer.js` (coordenação entre 2+ observers — ROADMAP 0056). ROADMAP 0029. |
| `config.js` | `get(path, fallback)` — único lugar de tunables: anda por `Memory.settings` (dot-path) → árvore `defaults` do módulo → `fallback` do chamador; nunca lança. ROADMAP 0012. |
| `autoscale.js` | Ajuste incremental genérico de contagem-alvo, por sala (ROADMAP 0040/0049). `register(role, {grow?, shrink?, maxCount?})` — `grow`/`shrink` recebem `(room, wanted, delta)` e devolvem uma pontuação de pressão (`0`/falsy = não elegível, `> 0` = elegível, maior = mais urgente); `maxCount(room)` devolve o teto **absoluto** desse role (fórmula base + delta combinados). `apply(room, wanted)` — muta `wanted` com o delta acumulado da sala (`Memory.rooms[name].autoscale.delta[role]`, nunca deixa o total abaixo de 0) e, só quando o cooldown **da sala** abriu (`Game.time - lastAdjustTick >= autoscale.cooldown`, default 30000 — compartilhado entre **todos** os roles registrados, não por role), escolhe o maior `grow` entre os elegíveis (crescer tem prioridade) ou, faltando isso, o maior `shrink` entre quem tem delta positivo pra devolver, aplica ±1 só nesse role, e reinicia o cooldown da sala. Por fim, **incondicional** (não depende do cooldown ter aberto): pra todo role com `maxCount` definido, `wanted[role] = Math.min(wanted[role], maxCount(room))` — cobre o caso em que a fórmula base **sozinha** já ultrapassa o teto (`builder` até 4, `hauler` até 5 sem link, ambos acima dos tetos atuais de 2/3), onde só bloquear o `grow()` não bastaria (ROADMAP 0049, generaliza o clamp manual de RCL8 que 0041 tinha só pro `upgrader`). Cada predicate (`grow`/`shrink`/`maxCount`) roda em `try/catch` próprio — uma que lançar é ignorada naquele tick, não derruba o resto (constitution §3). `rooms/needs.js`'s `upgrader` é o primeiro consumidor, seguido de `hauler`/`builder`/`pioneer`. |
| `combat.js` | `takeCover(creep)` (creeps não-combatentes se abrigam sob ataque), `flee`, `blockingMatrix`, `isArmed`, `hasMelee`, `threats`, `incomingDps(hostiles)` (ROADMAP 0036 revisão — dano/tick somado por composição de corpo, boost lido ao vivo de `BOOSTS[part.type][part.boost]`, nunca hardcoded; usado por `rooms/defense.js`'s `checkSafeMode()`), `safeRange()` (lida ao vivo de `config.get("combat.safeRange")`, não cacheada — ajustável sem redeploy). Primitivos de combate compartilhados entre `defender`/`defenderStriker`/`defenderMedic` (ROADMAP 0032 Fase 2, migrados do antigo `defender.js` — constitution §5): `KITE_RANGE`, `threatPriority`, `pickTarget`, `shoot`, `patch`, `kiteAwayFrom`, `ensurePartner(creep, partnerRole)` (pareamento via `memory.partnerId` nos dois lados), `nearestOwnRampart`. `silenceAttackAlerts(creep)` (ROADMAP 0052, paridade com `old_1`) — `creep.notifyWhenAttacked(false)`; chamado incondicionalmente por `scout`/`raider`/`squadDismantler`/`pioneer` (entrar em território hostil/estrangeiro é o próprio trabalho deles) e por `reserver` só em missão `"contest"`. |
| `squad.js` | Movimento/coordenação de squad em lockstep de verdade (ROADMAP 0032 Fase 4, O5) — `advance(creep, squadId)`, chamado por `defenderStriker`/`defenderMedic`/`squadDismantler` quando `memory.squadId` está setado; nenhum dos três sabe de `Memory.squads` por conta própria (constitution §5). Por tick: poda membro morto e promove novo líder se preciso (`pruneDeadMembers`); fora de sala perigosa (`isDangerousRoom` — sala-alvo original **fixa**, `squad.room`, não `squad.target.room`, que muda durante o recuo, **ou** qualquer sala com `enemies>0`), viaja sozinho via `routing.moveToRoom` como o `raider`; decide recuar (`squad.state`) se a média de hp cai abaixo de `squad.retreatHpRatio` **e** existe saída sem hostil conhecido, senão luta até morrer; escolhe formatura (`block` 2x2 ou `column` fileira única, testando se as 4 próximas tiles cabem — `shapeFits`, via `combat.blockingMatrix`) e só um dos 4 roda `PathFinder` por tick (`ensureDecision`, gatilhado por `Memory.squads[id].dirTick===Game.time`, não por "só o líder pode calcular" — evita depender de ordem de iteração do `Game.creeps`); bloqueio persistente vira `avoid` temporário depois de `stuckTicksLimit` ticks (mesmo princípio de stall guard do `architect.js`). `disband()` — limpa `squadId` de todo mundo só quando um squad recuando chega de fato em `squad.from` (não em "qualquer sala segura" — striker/medic não têm lógica de volta-pra-casa fora do modo squad). `registerPending(creep)` — promove `Memory.pendingSquad` pra `Memory.squads` assim que os 4 membros necessários existem. `missionComplete(squad)` (ROADMAP 0047) — lê só `Memory.rooms[squad.room].enemies`/`.enemyStructures` (já mantido por `rooms/intel.js`, sem `room.find` novo); `"siege"` só olha `enemyStructures` (dismantler não luta contra creep), qualquer outra missão exige os dois zerados. Chamado dentro do bloco `state==="advancing"` de `advance()`, logo depois de `maybeRetreat()` — quando verdadeiro, dispara a mesma transição pra `"retreating"`/`target={room:from}` já testada pelo recuo por HP, então um squad `"combat"` que limpa tudo (creeps + `defenderStriker`'s mop-up de estrutura, ver `roles/`) volta pra casa sozinho em vez de ficar parado pra sempre no centro da sala. |
| `move.js` | `travel(creep, target, opts)` — cache de rota em `creep.memory._m`, repath quando preso, swap-com-parado (creep móvel), pedido de licença via `utils/excuseMe.js` (creep parado — ROADMAP 0044), `CostMatrix` por sala no heap. `nativeMoveTo` capturado para fallback. Só same-room; alvo em sala diferente cai direto pro `nativeMoveTo` (`costCallback` passa intacto). |
| `excuseMe.js` | Cortesia de tráfego (ROADMAP 0044) — `ask(mover, nx, ny)`, chamado por `move.js`'s `travel()` quando a próxima tile do caminho tem um creep aliado parado (`isParked`). Caminha em linha reta a partir de `(nx, ny)` coletando qualquer fila de creeps parados na mesma direção (até `excuseMe.maxChain`, default 4 — corredor de 1 tile, não busca geral; `NEVER_ASKED = {miner: true}` para a coleta ali mesmo, sem incluí-lo — o miner nunca negocia sua seat do container, `roles/miner.js`'s próprio re-seat é quem decide onde ele fica, e um miner mais à frente na fila também nunca é "atravessado", só quem vem antes dele pode sair sozinho pro lado), escolhe uma tile de saída pro último da fila (`pickExitTile`, entre reto-à-frente e as 8 tiles adjacentes a ele) e move a fila **inteira** nesse tick (`mover.say("Excuse-me")` + `blocker.say("Ok!")` por bloqueador) — o motor do Screeps resolve nativamente o encadeamento "todo mundo anda uma casa" quando o último pousa numa tile vazia, sem swap 1:1 escrito à mão nem estado em Memory. A tile de saída prefere ficar dentro de uma "âncora" de trabalho do bloqueador (`anchorsFor`, follow-up a pedido do usuário) — controller a alcance 3 pra um upgrader, ou o container/link debaixo dele agora (qualquer role, mesma checagem que `isParked` já usa) — só cai pra "qualquer tile livre" (reta à frente primeiro) se nenhuma candidata bater com nenhuma âncora; essa preferência só vale pro último da fila, quem vem antes dele é sempre forçado a ocupar a tile vagada pelo de trás. Sem creep elegível na fila (ex.: o próprio bloqueador imediato já é um miner) ou sem tile válida pra ninguém nela, devolve `false` e `travel()` volta a rodear (comportamento anterior). |
| `routing.js` | Roteamento **entre salas** pra um destino específico (não a exploração do scout): `isHighwayRoom(roomName)` (x%10==0 ou y%10==0 — corredor aberto/sem dono), `isBlacklisted(roomName)`/`blacklistRoom(roomName)` (ROADMAP 0058 — `Memory.rooms[x].routeBlacklistUntil`, TTL `routing.blacklistTicks`; detecção por posição em vez de nome de sala — mesma x/y/sala numa coordenada de borda (0 ou 49) por 3 ticks seguidos — `keyPrefix` mantém a checagem própria do `moveToRoom` (`"_routeBorder"`) e a do scout na exploração livre (`"_exploreBorder"`) sem colidir no mesmo creep; `nudgeAwayFromBorder` anda 1 tile pra dentro via `creep.move()` direto, nunca junto de `moveTo()` no mesmo tick), `borderNeighborRoom(creep)` (ROADMAP 0060, correção no mesmo dia — o usuário testou ao vivo e viu o creep sair da borda mas nunca recalcular rota, porque `moveToRoom` blacklistava `creep.room.name`, a sala em que o creep **ainda está**, que `routeCostCallback` sempre permite não importa o blacklist; `borderNeighborRoom` lê `Memory.rooms[x].exits` pro lado específico do eixo travado — top/right/bottom/left conforme x/y é 0 ou 49 — e devolve a vizinha de verdade, a armadilha real; `null` sem intel de `exits` ainda, nunca um chute), `moveToRoom(creep, toRoomName, opts)` (as acima num só passo — detecta `isRouteFlapping` e depois `isStuckAtBorder`, blacklistando a sala-armadilha (`borderNeighborRoom(creep) || creep.room.name` — a vizinha identificada, só caindo pra sala atual sem intel) e, no segundo caso, nudgeando antes de sequer tentar `moveTo()` de novo naquele tick; nunca chama `PathFinder.search` por conta própria). Cruzar de sala cai direto no `nativeMoveTo` (via `move.js`'s `travel()`, que só intercepta same-room), sem sinal de "inalcançável" — uma checagem prévia via `PathFinder.search` (uma vez por sala entrada) foi tentada aqui e revertida: um scout passando por várias salas-armadilha em sequência (dando blacklist e escolhendo alvo novo a cada tick) disparava várias buscas não-cacheadas em rajada rápida o bastante pra esvaziar o bucket de CPU na prática, mesmo cada busca sendo barata isolada. A detecção de "essa sala está selada rumo ao alvo" é só do lado de quem já faz isso sem `PathFinder` (`isRouteFlapping`/`isStuckAtBorder` aqui, `roles/scout.js`'s `isFlapping()` + a mesma `isStuckAtBorder` reusada do lado da exploração — mesmo princípio do `m.stuck` do `move.js`/`stuckTicks` do `squad.js` — reativo, só contabilidade de tick/sala/posição, nunca busca de caminho). `global.routeCheck(fromRoomName, toRoomName)` (console) — diagnóstico manual, não roda todo tick: mostra a rota sem restrição e a rota `blockHostiles`, e lista qual sala hostil da rota direta está bloqueando quando `blockHostiles` não acha nada. `reserver` tem seu próprio stall guard (contador de ticks parado na borda, aviso único no console) pra quando `blockHostiles` corretamente recusa cruzar uma sala hostil de verdade e não existe rota alternativa — complementado pelo blacklist automático do 0058, que tenta achar uma rota alternativa antes de chegar a esse ponto. Usado por `signRoom`/`planLayout` do scout e pelo `reserver` (`blockHostiles: true` — nunca põe o pé numa sala com hostil visto). ROADMAP 0028. |

### `src/rooms/`

| Module | Papel |
|--------|-------|
| `intel.js` | Preenche `Memory.rooms[name]` a cada tick a partir de census + roomCache. Exits, sources, minerals, `defenseActive`, contadores `numberOf*`, `controllerLevel` (RCL de qualquer sala vista, não só própria) e `hasInvaderCore` (do mesmo `find()` de `enemyStructures` — ROADMAP 0032 Fase 3, usados por `rooms/raiding.js`). |
| `needs.js` | `roomNeeds(room)` — **decide a contagem-alvo de todos os roles** a partir do estado da sala (RCL, sources, containers, link network, storage, backlog de canteiros, hostis). Cacheado por tick. Todo `role.wanted` lê daqui. **Cuidado ao adicionar um role aqui**: `compute()` calcula a variável local e precisa dela **também** no `return {...}` final — um bug real (ROADMAP 0037 follow-up) computou `pioneer` mas esqueceu de incluir no `return`, deixando `roomNeeds(room).pioneer` sempre `undefined` e `pioneer.spawn()` sempre falso (`0 < undefined` é `false` em JS) sem nenhum erro/exceção pra denunciar — só um role que nunca spawnava. ### `src/roles/` (ordem de prioridade no `index.js`)

`bootstrap` → `defender` → `defenderStriker` → `defenderMedic` → `miner` →
`hauler` → `pioneer` → `upgrader` → `builder` → `reserver` → `remoteMiner` →
`remoteHauler` → `mineralMiner` → `scout` → `raider` → `squadDismantler`.
`mineralMiner` (ROADMAP 0051) tem `wanted()`/`spawn()` self-contidos, não
passa por `rooms/needs.js` (sem disputa de recurso com a economia de
energia). Contagens de todos os outros
vêm de `rooms/needs.js`; `scout`/`raider` são pulados no loop principal do
`spawning.js` e só entram no fim, se mais nada (nem o outro dos dois)
quiser nada — puro oportunismo. `squadDismantler` nunca aparece nesse loop
— `wanted()`/`spawn()` sempre devolvem 0/`false`, ele só nasce via
`raiding.spawnPendingSquad` (ROADMAP 0032 Fase 4).

- **bootstrap** — faz-tudo de emergência (`WORK CARRY MOVE`). `wanted` = 0 quando há miner + hauler (ou link network); 1 senão. Cobre o pré-container e a recuperação pós-ataque. Entrega: spawn/extension empatados no topo (o mais perto por range — ROADMAP 0043, antes era spawn incondicional primeiro e extension só empatava com link coletor/container no segundo nível) → link coletor/container → dropa no chão se não tiver pra onde.
- **defender** — kiter RANGED solo, generalista (tiro+cura no mesmo corpo). Fallback quando `room.energyCapacityAvailable` ainda não cobre `defenderStriker`+`defenderMedic` (`defender.pairEnergyThreshold`, default 500 — ROADMAP 0032 Fase 2); acima disso `rooms/needs.js` zera sua contagem e passa a querer o par. Atira + se cura todo tick; foge de melee a alcance ≤ 3; corpo ~1:1 MOVE, `MOVE` sempre por **último** no array (dano ataca por índice — proteger a fuga vale mais que proteger a arma pra um kiter; ROADMAP 0032 D1). Alvo/tiro/cura/fuga vêm de `utils/combat.js`, compartilhados com os dois roles abaixo.
- **defenderStriker** — metade `RANGED_ATTACK` da dupla (ROADMAP 0032 D2), corpo 1:1 `RANGED_ATTACK`:`MOVE` sem `HEAL` (`MOVE` por último). **Modo casa** (sem `memory.squadId`): pareia com um `defenderMedic` via `combat.ensurePartner` (`memory.partnerId` nos dois lados). Postura de tanque (D3): segura na rampart própria mais perto — nega melee de vez (rampart bloqueia movimento, não dano — só protege enquanto o hostil não consegue chegar a alcance 1) sem prever de antemão se a tile está "selada"; uma brecha aparece como "melee ainda no alcance" no mesmo tick e cai pro kite de sempre. Sem rampart por perto ou sem parceiro, kita igual ao `defender` solo (sem self-heal — não tem `HEAL`). Mop-up (O1): sem ameaça de melee, fecha em alcance 1 num alvo **ferido** dentro de `defender.mopUpRange` (10 tiles da spawn) pra terminar, em vez de só segurar `KITE_RANGE`. **Modo squad** (`memory.squadId` setado, ROADMAP 0032 Fase 4): pula a postura de casa inteira, posicionamento vem de `utils/squad.advance` — só atira no que estiver a alcance. Sem creep hostil (mas ainda com estrutura hostil na sala), ataca `FIND_HOSTILE_STRUCTURES` a `combat.KITE_RANGE` em vez de ficar parado (ROADMAP 0047, mesma exclusão de `STRUCTURE_POWER_BANK` que `raider`/`squadDismantler`) — junto com `squad.missionComplete()` (ver `utils/squad.js`), é isso que faz um squad `"combat"` de fato terminar a limpeza da sala e voltar pra casa.
- **defenderMedic** — metade `HEAL` da dupla, corpo 1:1 `HEAL`:`MOVE` sem armas (`MOVE` por último). **Modo casa:** segue o parceiro a alcance `KITE_RANGE-1`, cura via `combat.patch` (self primeiro, depois aliado ferido mais perto). Sem parceiro, ainda cura quem estiver por perto. **Não** usa `utils/combat.takeCover()` (esse dá um raio de segurança de `safeRange`, 5 tiles, de qualquer ameaça — brigaria com o próprio trabalho do medic de ficar perto o bastante pra curar em combate); só foge quando um melee está **adjacente** a ele mesmo (perigo real e imediato). **Modo squad:** posicionamento vem de `utils/squad.advance`, continua curando via `combat.patch` (já cura "o aliado ferido mais perto", normalmente um companheiro de squad).
- **miner** — estático sobre um container de source (re-seat por tick via `memory.seat`; empurra squatter não-miner do assento). Só harvesta se tiver pra onde mandar (`hasDepositTarget`): container com espaço, ou (container cheio) link coletor/torre com espaço; sem nenhum dos dois, para de minerar naquele tick em vez de espalhar energia no chão pra decair à toa. WORK-heavy; `+CARRY` a partir do RCL 3 → `distribute()`: enche a torre de source até a reserva **sempre** (prioridade incondicional — o hauler nunca ajuda nessa torre, ROADMAP 0026), senão link coletor, senão container, e só topa a torre **além** da reserva se houver excedente de verdade (spawn/ext cheios ou buffers locais cheios). Substituição cronometrada por spawn + viagem ciente de fadiga; `spawn()` decide por source.
- **hauler** — único role de transporte (absorveu o `harvester`). `CARRY×2 MOVE`, modos `load`/`deliver`. **Carrega** (ROADMAP 0043 reordenou, adicionou o piso de decaimento e o terminal): **terminal** primeiro — mas só a fatia que o `terminalLedger` (`Memory.rooms[x].terminalLedger`, `{amount, withdrawable, sinceTick}`) credita como retirável (`utils/hauler.terminalWithdrawable`, recalculado 1×/tick/sala): o saldo que já está lá na **primeira vez** que o código observa o terminal vira baseline **e já liberado** pra retirada (sem histórico não dá pra saber a origem, e proteger pra sempre deixava um saldo pré-existente preso indefinidamente — bug real de produção, ROADMAP 0043 follow-up); a partir daí, um aumento só vira `withdrawable` se tiver uma transação de entrada registrada explicando (`Game.market.incomingTransactions` — cobre tanto `Terminal.send` de sala-irmã quanto ordem de mercado liquidada a favor da sala, filtradas por `to === room.name`, `resourceType === RESOURCE_ENERGY` e `time` mais novo que o do último check, pra nunca contar a mesma transação duas vezes); um aumento **sem** transação correspondente (depósito manual pela UI) fica de fora — o jogador já decidiu o que fazer com aquilo. Console `resetTerminalLedger(roomName)` reseta um ledger preso (ex.: salvo por um build anterior a essa correção) — o próximo tick trata o saldo atual como baseline nova, já liberado. Reduções (retirada do próprio hauler, `Terminal.send` de saída, venda no mercado) encolhem o piso credenciado no mesmo tanto, nunca deixando o ledger reivindicar mais do que existe fisicamente. `Game.market` ausente (bot sem terminal configurado, ou stub de teste) nunca lança — trata como zero transações. **Piso do terminal** (ROADMAP 0054, em cima do ledger, não no lugar dele): `terminalWithdrawable()` nunca devolve mais do que deixaria o terminal acima de `logistics.terminalReserveRatio` (10%) da própria capacidade — aplicado na leitura (`current − floor`, sem persistir em Memory), então o ledger continua controlando *o que é retirável em teoria* e esse piso controla só *quanto disso pode ser sacado agora*. Withdraw do terminal é **marcado (`dest:"storage"`)** pra ir direto pro storage na entrega, pulando toda a cascata normal — depois: drop **decay-aware** acima de `hauler.minDropLoad` (100) **na chegada** (`estimatedDropAmount` — `amount − ⌈amount/hauler.dropDecayDivisor⌉ × alcance` até a pilha; alcance é proxy barato de ETA, não PathFinder por candidato — mesma troca que o `pioneer.js` já faz pra minerar local) → tombstone/ruína (mesmo piso, sem decaimento por tick) → link da base → **storage**: incondicional quando spawn/ext/uma torre **crítica** precisam (`essentialConsumer` — manter a sala apta a spawnar/defender vale mais que a reserva; sala jovem raramente chega nem perto de 1% de um storage de 1M, e travar isso nessa conta faria a sala morrer de fome por causa de um buffer que ninguém pediu pra proteger tanto — bug real do follow-up do 0043, corrigido; torre `sourceDefense` **não** conta como essencial — só o miner a alimenta, o `pickDeliver` nunca mira nela), ou, só acima da reserva (`utils/resourceTiers.aboveReserve`, 1% — ROADMAP 0054, substituiu o antigo `hauler.storageReserveFloor` de 5%), quando lab/container do controller precisam (`optionalConsumer`) **ou** uma torre na **banda ideal** ainda vale topar (`toppableTower`/`towerDeliverable`, `>= tower.satisfactoryRatio` **e** `freeCapacity > hauler.toppingOffThreshold`) — nunca storage→storage em nenhum dos casos. Uma torre na **banda satisfatória** (entre `tower.criticalRatio` e `satisfactoryRatio`, 50–80% por padrão) não conta pra nenhum dos dois — nem crítica, nem vale topar — fica simplesmente de fora até cair ou subir de banda (ROADMAP 0054: antes era um único limiar com "acima disso é incondicional pra sempre", inclusive esvaziando storage pra uma torre já quase cheia sem gate nenhum — bug real que motivou a spec) → container de source **mais próximo com mais de `MIN_CONTAINER_LOAD` (1000) de energia** (não o que tem mais energia guardada; container vem **depois** de storage, não antes). Pula pilha já reservada por outro picker de maior prioridade (`utils/reservations`). **Entrega**: torre **crítica** (`< tower.criticalRatio`, 0.5 — ou `criticalRatioUnderAttack`, 0.8, sob `defenseActive`) → spawn/ext → **storage abaixo da reserva de 1%** (buffer de emergência vale mais que topar torre/lab além da banda satisfatória) → torre na **banda ideal** (`>= tower.satisfactoryRatio`, 0.8/0.95 sob ataque) ainda com mais de `hauler.toppingOffThreshold` (5%) livre → **lab** com espaço → storage (geral, o que sobrar) → container do controller — **nunca** numa torre de defesa de source (`sourceDefense` no plano, `isSourceDefenseTower`), essa é só do miner (ROADMAP 0026); um load marcado `forcedDeliver:"storage"` (terminal) ignora essa cascata inteira e mira o storage direto enquanto ele existir e tiver espaço, só caindo de volta pra cascata normal se não tiver storage ou ele estiver cheio — a marca só some quando o tanque esvazia de novo (`job` volta pra `"load"`). `pioneer` continua vencendo o hauler em qualquer disputa por pilha (`utils/reservations`, rank 2 > 1, sempre — não mudou). Contagem: `1 + sources sem link coletor` com link network, `min(5, containers+1)` sem — piso sobe pra `hauler.minCountWithMineral` (2) quando há extractor+container de mineral ativos (`mineralAmount > 0`) e storage pra receber (ROADMAP 0055: o errand de mineral abaixo compete por ciclos com a vazão de energia; volta ao piso normal com o depósito esgotado). **Fallback de mineral/lab/factory/power** (ROADMAP 0051, menor prioridade possível — decisão do usuário, revisando um `mineralHauler` role dedicado que teria ficado ocioso quase sempre): só quando `pickLoad()` não acha nada de energia **e** o tanque está vazio, tenta `pickMineralJob()` — esvazia o container do mineral pro storage/terminal, escoa a lab de saída de uma reação ativa, reabastece a lab de entrada mais vazia, escoa/reabastece o factory de uma produção ativa, alimenta o power spawn com Power — nessa ordem de prioridade. Uma vez aceito (`memory.mineralJob = {resourceType, fromId, toId}`), o hauler termina esse job (pickup → deliver) antes de voltar pra lógica de energia, nunca abandona um recurso pela metade no próprio `store`. `optionalConsumer()` (energia pro lab/factory/power spawn, não os recursos não-energia) ganhou `STRUCTURE_FACTORY`/`STRUCTURE_POWER_SPAWN` na mesma lista que já tinha `STRUCTURE_LAB`.
- **pioneer** — resgata uma sala própria sem spawn nenhum (recém-claimada, ou que perdeu o último num ataque — ROADMAP 0037, `rooms/pioneering.js` decide elegibilidade, mesmo papel de `remotes.js`/`raiding.js` pro próprio domínio). Corpo `WORK`:`CARRY`:`MOVE` 1:1:1 (`scaledBody`, mesma proporção do `builder`). Na sala-mãe, enche a `CARRY` antes de sair (`utils/energy.energyPiles`, compartilhado com o `builder` — constitution §5) — o ponto é chegar com o tanque cheio, não gotejar energia em várias viagens pela metade. Prioridade **máxima** em qualquer disputa por pilha — `utils/reservations.js`'s `pickerRank` dá ao pioneer o rank mais alto (2, acima até de hauler/bootstrap), e diferente deles, essa prioridade vale **sempre**, sala estável ou não (ROADMAP 0037 follow-up). Na sala-alvo, constrói **só** o construction site do spawn que o `architect.js` já planta sozinho assim que a sala vira `my` até ele ficar pronto; a partir daí, se sobrar qualquer outro canteiro (extension, container, estrada, ...), continua construindo — o mais perto por range, sem heurística de "mais perto de terminar" como o `builder` (ROADMAP 0043: uma sala com spawn e mais nada ainda não consegue spawnar seu próprio builder por um tempo, então esse WORK vale mais terminando a base do que virando bootstrap cedo). Esvaziou com o trabalho ainda por fazer: compara minerar uma source local (`FIND_SOURCES` com `energy>0` na própria sala-alvo, tempo de viagem em range + tempo de encher `store.getCapacity/(`WORK`×`HARVEST_POWER`)`) contra a viagem redonda pra sala-mãe (`remotes.roomDistance × claim.ticksPerRoomHop` × 2, mesmo orçamento que o `claimRoom` já usa pra distância) e commita na opção mais rápida (`memory.miningLocal`, sticky feito `memory.returning`, pra não ficar recalculando toda hora); nenhuma das duas dá margem suficiente e ele já tem WORK — ainda assim decide (nunca fica ocioso). Só quando **não sobra nenhum canteiro** — spawn e resto da base prontos — é que, em vez de se aposentar, **vira um `bootstrap`** ali mesmo (`creep.memory.role = "bootstrap"`, limpa `targetRoom`/`home`, delega pro `bootstrap.run(creep)` na hora — mesmo princípio da migração `harvester`→`hauler` que o `main.js` já faz, ROADMAP 0014, só que aqui dentro do próprio role porque depende de estado específico do pioneer que o `main.js` não tem por quê saber). Corpo do pioneer (escalado pela sala-mãe) tende a ser maior que o de um bootstrap normal (`[WORK,CARRY,MOVE]` fixo) — ganho de graça, não desperdício de um creep já carregado e já lá. Nunca despachado pra sala-alvo com hostil visto, nem enquanto a sala-mãe está sob ataque (mesma cautela de `reserver`/`raider` em `rooms/needs.js`). `mothersFor` inclui **toda** sala própria **com spawn** dentro de `pioneer.maxDistance` (default 30, `remotes.roomDistance`, hops de rota) — não só a mais próxima: cada uma manda sua própria dupla (`pioneer.maxConcurrent`, default 2, é um teto **por sala-mãe**, não compartilhado entre elas). Prioridade na fila de spawn fica logo depois de `hauler` — a sala-mãe nunca sacrifica a própria sobrevivência básica pra ajudar outra, mas ajuda vem antes das melhorias (upgrader/builder/scout).
- **upgrader** — máquina de estados. Vira builder quando o controller está no máximo e seguro. Cede pilha de energia a hauler/bootstrap enquanto spawn/ext não estão cheios (`utils/reservations`) **quando outro creep de rank maior disputa a mesma pilha nesse tick** — isso sozinho não bastava (bug real relatado em produção, ROADMAP 0054 follow-up): storage/container é estoque da sala inteira pensado pra spawn/ext primeiro, e nenhum hauler precisa estar mirando aquele pote especificamente pro upgrader esvaziá-lo (ex.: um source container que acabou de encher de novo depois da sala secar). Por isso o saque de storage/container (não o link — esse já vem pré-aprovado pelas próprias tiers do `structures/link.js`) só acontece quando `reservations.economyStable(room)` (spawn/ext já cheios) **ou** `utils/resourceTiers.controllerCritical(room)` (controller genuinely perto do downgrade) — caso contrário cai nos fallbacks que não competem com o estoque da sala (minerar uma source por perto, ou esperar parado perto do link receptor). Caso real que motivou o fix: RCL8, `ticksToDowngrade` 194864 de um teto de 200000 (sem risco algum) e o upgrader ainda assim drenando tudo que aparecia. Contagem escala com energia no storage.
- **builder** — build oportunista de qualquer canteiro em alcance 3 (sem checar dano) + repair oportunista **só de crítico** em alcance 3 (<30% pra estrutura normal, `rampartRepair.isCritical` pro rampart — mesma barra do repair crítico da etapa principal, ROADMAP 0043: antes usava um teto plano de 35% e `worthHardening` pro rampart, então um rampart já "saudável" ou uma estrutura só arranhada sequestrava o builder do alvo de verdade só por estar em alcance); depois repair < 30% → canteiros (console `prioritizeBuild(ids)` força uma ordem, autolimpa — ROADMAP 0021) → repair → ramparts → upgrade. Repair de estrada respeita `traffic.worthRepairing` — pula uma planejada fria (sem tráfego recente). Torre nunca é excluída do repair (nem na etapa oportunista nem na crítica) — só some da lista quando `s.hits/s.hitsMax` não bate o teto. Rampart usa os três níveis de `utils/rampartRepair.js` que o `tower.js` também usa (ver abaixo) só no fallback de último recurso (`damagedRamparts`, depois de canteiros e repair normal, via `worthHardening`) — as etapas oportunista e crítica usam a fatia mais estreita (`isCritical`) das duas, `damagedRamparts` é quem ainda enxerga o nível "saudável"/"com sobra de energia". Pega energia do pool mais próximo (drops/tombstones/ruins/links/containers/storage), **cedendo a pilha p/ hauler/bootstrap enquanto spawn/ext não estão cheios** (`utils/reservations`); **nunca minera uma source diretamente** — sala seca = esperar perto do link receptor (e sacar dele assim que chegar a alcance, mesmo que a disputa de reserva tenha negado a pilha antes — senão fica parado pra sempre do lado de energia real), não disputar o assento do miner. Contagem = `min(backlog de canteiro, energia disponível na sala)` — `pickableEnergy` (storage + drops + tombstones + ruínas + containers + links receptores) evita builder ocioso com a sala seca.
- **reserver** — role único com três missões (`memory.mission`, ROADMAP 0020 + 0046). `"reserve"` (uma por remote pendente em `Memory.rooms[mãe].remotes`, corpo `CLAIM×N` escalado) mantém o controller remoto reservado (`reserveController`); `"claim"` (**1 só no império**, como o `scout`, corpo fixo `[CLAIM, MOVE]`) domina a sala de vez (`claimController`), disparada por `Memory.claimTarget`. **`"contest"`** (ROADMAP 0046, corpo `CLAIM×N` escalado como `"reserve"` — mais `CLAIM` = cerco mais rápido) — enquanto o controller ainda tem dono ou reserva de outro jogador, martela `attackController()` todo tick; assim que fica neutro, muda pra `claimController()` igual à missão `"claim"`. Diferente do `"claim"`, morrer no meio do cerco **não** é beco sem saída — é o resultado esperado de um `attackController()` de longo prazo (corpo com `CLAIM` só vive 600 ticks) — `rooms/needs.js` só respawna enquanto `Memory.contestTarget` existir, sem checagem de abandono por morte. Viaja com `routing.moveToRoom` (`blockHostiles: true` — nunca atravessa sala com hostil visto, prioriza sala highway — ROADMAP 0028). Marca `Memory.claimTarget.creepSeen=true` a cada tick vivo (só a missão `"claim"`) — se o creep sumir sem nunca ter limpado `Memory.claimTarget` sozinho (sucesso ou beco sem saída), `rooms/needs.js` percebe que morreu em trânsito e desiste em vez de spawnar outro pra sempre (ROADMAP 0035).
- **remoteMiner** — como o `miner`, mas numa sala remota (`memory.home`/`memory.targetRoom`); só conta em `remotes.active()`. Constrói/repara o próprio container (sem rodar `architect` — a sala não é minha); hostil na sala remota → recua pra casa. Viaja com `remotes.roomCallback` (só sala minha/reservada + alvo — inalterado pelo 0028).
- **remoteHauler** — como o `hauler`, mas rota fixa remote↔mãe; carrega de container/drop na sala remota, entrega em storage/spawn/ext da mãe; recua vazio se a sala remota ficar hostil. Mesmo `remotes.roomCallback` do `remoteMiner`.
- **mineralMiner** (ROADMAP 0051) — senta no container do mineral (já plantado pelo `architect.js`), minera (`WORK`-heavy, sem `CARRY` — overflow cai automaticamente no container por baixo, mesmo mecanismo nativo que o `miner` já usa pra energy) enquanto `mineral.mineralAmount > 0` e o container tem espaço. `wanted()`/`spawn()` self-contidos (não passa por `rooms/needs.js`).
- **scout** — **1 por império** (extras se suicidam). Duas tarefas com destino fixo, prioridade nessa ordem, ambas via `routing.moveToRoom` (prioriza sala highway, penaliza — sem bloquear — sala com hostil visto, ROADMAP 0028): assina o controller de uma sala em `Memory.signQueue` (console `signRoom(room, text)`); prévia de layout de uma sala em `Memory.layoutRequests` que nenhum observer cubra (console `planLayout(room)`/`cancelLayout(room)`/`layoutQueue()` — pula sala já coberta por `utils/observer.observerFor`; fica parado na sala alimentando `architect.planCity(room, {preview:true})` via `main.js` até `Memory.rooms[room].planned`, com stall guard `routing.layoutWaitLimit` — desiste e loga em vez de acampar pra sempre). Sem nenhuma das duas: se existe algum observer (`utils/observer.hasAnyObserver()`), se aposenta (`suicide`) em vez de vagar — a exploração é dele agora (ROADMAP 0029); senão, round-robin de salas adjacentes não vistas (exploração — não usa `routing`, sem destino fixo pra rotear). Resto do M1 → ROADMAP 0009.
- **raider** — despachado em `Memory.raidTarget` (console `raidRoom`/`raidRemote`, `rooms/raiding.js` — ROADMAP 0032 Fase 3, O2/O4, e 0036, O3). Corpo `RANGED_ATTACK`+`MOVE` puro (sem `HEAL` — raid é pra ser rápido e barato, não sustentado). Viaja via `routing.moveToRoom`; luta hostil armado se houver (`combat.threats`/`shoot`, recua só de melee realmente adjacente). `memory.mission` (default `"raid"`, do `Memory.raidTarget.mission`): **`"raid"`** — sem hostil armado, ataca a primeira `FIND_HOSTILE_STRUCTURES` (o invader core, tipicamente) a `KITE_RANGE` via `rangedAttack` — funciona em estrutura tanto quanto em creep, não precisa de `ATTACK`/alcance 1; sem mais nada, limpa `Memory.raidTarget` e se aposenta (`suicide`) — sucesso, não erro. **`"harass"`** (O3) — sem hostil armado, ataca `FIND_HOSTILE_CREEPS` sem filtrar por armamento (reserver/miner são desarmados de propósito, nunca aparecem em `combat.threats`), **nunca** toca `FIND_HOSTILE_STRUCTURES` (a missão é negar economia, não invadir); sem nenhum hostil (armado ou não) agora, se aposenta sem revisitar — baixo compromisso de propósito, não fica acampado numa remote esperando um respawn. Role separado de `defenderStriker`/`defenderMedic` de propósito (mais simples — sem parceiro, sem tanque, sem mop-up), só reaproveita os primitivos de `utils/combat.js`.
- **squadDismantler** — metade `WORK` de um squad de cerco (`mission:"siege"`, ROADMAP 0032 Fase 4), corpo 1:1 `WORK`:`MOVE`. Sempre modo squad — sem `memory.squadId`/`memory.pendingSquad` ele se aposenta (`suicide`) na hora, nunca vaga sozinho. Posicionamento inteiro vem de `utils/squad.advance`; a única lógica própria é `dismantle` na primeira `FIND_HOSTILE_STRUCTURES` adjacente (fila/rampart inimiga tipicamente). Não ataca creep — isso é trabalho do `defenderMedic`+outro membro do squad ou, na composição `"combat"`, de dois `defenderStriker`.

### `src/structures/`

- **tower** — prioridade de alvo (HEAL > RANGED > ATTACK), mass-attack quando cercada, cura, e então repair (só estruturas planejadas, respeitando `traffic.worthRepairing` pra estrada) acima de 70% de energia (`tower.repairEnergyRatio`). Rampart/wall usa `utils/rampartRepair.js` (ROADMAP 0032 D4 + follow-up — única fonte de verdade, também usada pelo `builder.js`, pra nunca haver duas leituras divergentes do mesmo critério): tudo em FRAÇÃO do próprio `hitsMax` da estrutura (nunca um número fixo — `hitsMax` já escala com RCL via `RAMPART_HITS_MAX`/`WALL_HITS_MAX`), três faixas — `< tower.rampartCriticalRatio` (0.1%) é crítico, sempre a prioridade máxima entre as estruturas defensivas; `< tower.rampartHealthyRatio` (1%) é "saudável", sempre reparável, mesma prioridade de quem está crítico só que sem furar a fila; **acima de 1%** só continua evoluindo enquanto `utils/resourceTiers.aboveReserve(room)` (ROADMAP 0054 — reserva única de 1% do storage, substituiu um gate próprio de 50% de fill) — sem isso, um único rampart já construído (o resto ainda só canteiro) vira o único alvo defensivo existente e absorve energia indefinidamente rumo ao `hitsMax` (até 300M no RCL8) mesmo sem sobra real de energia na sala. O próprio *enchimento* da torre (quando o `roles/hauler.js` a considera crítica/satisfatória/ideal pra fins de entrega) é decidido inteiramente no `hauler.js` — ver `tower.criticalRatio`/`satisfactoryRatio` (ROADMAP 0054) abaixo.
- **link** — o link coletor decide entre o link do controller e o do storage por proximidade + urgência, não mais "quem tem mais capacidade livre" (ROADMAP 0054, "Link tiers"). Classifica cada link não-coletor em runtime (`findInRange`/`inRangeTo(controller, 3)` = link do controller; o outro = link do storage — mesmo padrão geométrico de `utils/energy.receivingLink()`); com só um dos dois construído (RCL baixo) ou mais de dois links não-coletores, cai no fallback antigo (mais capacidade livre). Com os dois presentes, em ordem: (1) `utils/resourceTiers.controllerCritical(room)` (`ticksToDowngrade` abaixo de `logistics.controllerCriticalDowngradeRatio`, 10%, de `CONTROLLER_DOWNGRADE[rcl]` — mesma função reaproveitada por `roles/upgrader.js`, ROADMAP 0054 follow-up) → sempre pro link do controller, mesmo com o do storage vazio; (2) fill do storage abaixo de `logistics.reserveRatio` (1%, via `utils/resourceTiers.aboveReserve`) → link do storage (emergência simétrica); (3) storage `>= logistics.storageSatisfactoryRatio` (50%) **e** `rcl < 8` → link do controller (controller ainda tem RCL de verdade pra ganhar, não faz sentido inchar um storage já confortável); (4) default → link do storage.
- **rampart** — abre (`setPublic`) para um creep aliado a ≤ 1 tile, fecha quando ele sai; não abre se um inimigo está a ≤ 2 tiles.
- **observer** — 1 `observeRoom()` por tick (`utils/observer.js` pro alcance). Prioridade: (1) uma entrada de `Memory.layoutRequests` dentro do alcance e ainda não `planned` (e limpa/loga qualquer uma já `planned` que encontrar — é o único lugar que desenfileira pro caso de uma sala vista por observer, não por scout); (2) uma entrada de `Memory.observeRequests` dentro do alcance e ainda não expirada (console `observe(roomName, ticks=10)` — ROADMAP 0030; expira (`Game.time >= prazo`) **antes** de checar alcance, então uma sala fora do alcance de todo observer ainda assim se limpa sozinha, nunca fica presa na Memory); (3) sem nada pendente, `explorePriority` — mesma ideia do round-robin antigo do scout (toda sala alcançável, não só saídas adjacentes), mas por score em vez de puro "menos visto": `staleness * (1 + enemies * config.get("observer.militaryWeight", 1))`, `staleness = Game.time - lastVisit`, `enemies = Memory.rooms[x].enemies || 0` — sala com mais hostil visto é revisitada mais, mas o score de qualquer sala cresce sem limite com o tempo, então nada fica sem visita pra sempre (`militaryWeight=0` volta ao critério antigo). Sala nunca vista ainda vence tudo de cara (nem entra no score). `roomNameToXY`/`xyToRoomName` convertem nome de sala em coordenada de mundo com sinal, pra varrer o quadrado de alcance por aritmética em vez de chamar `getRoomLinearDistance` por sala candidata. ROADMAP 0029/0030/0031.
- **lab** (ROADMAP 0051) — só a lab de saída (`Memory.rooms[x].labReaction.output`, decidido por `rooms/refining.js`'s `setLabReaction()`) age: chama `runReaction(input1, input2)` quando as duas labs de entrada existem e `cooldown===0`. As labs de entrada em si são no-op (`run()` confere o id e sai) — a reação roda exatamente 1x por sala por tick, mesmo padrão do `tower`/`link`.
- **factory** (ROADMAP 0051) — com `Memory.rooms[x].factoryProduct` setado (`setFactoryProduct()`), `cooldown===0`, e todo componente da receita (`COMMODITIES[product].components` — constante nativa do Screeps, nunca hardcoded) já estocado, chama `produce(product)`. Estocar/escoar é `roles/hauler.js`'s `pickMineralJob()` (não-energia) + `optionalConsumer()` (energia).
- **powerSpawn** (ROADMAP 0051) — com `store[RESOURCE_POWER] >= 1`, chama `processPower()` incondicionalmente (sem checar energia própria — o motor recusa sozinho, fail-soft, se faltar); `powerSpawn.enabled` (`config.js`) desliga se preciso. Conseguir Power em primeiro lugar (invasão de power bank, ou mercado) é fora de escopo — ver ROADMAP "Later".
